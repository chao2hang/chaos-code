## 可移植性与风险评估（结论，未执行任何移植）

1. **`xai-grok-update`：上游新增 `winget.rs` / `windows_payload.rs` / `cleanup_downloads.rs`，
   并且改了 `auto_update.rs`、`lib.rs`、`version.rs`、`Cargo.toml`。** 这是本轮最需要先决策的一项：
   - `winget.rs` 的 `INSTALL_COMMAND = "winget install --id xAI.GrokBuild -e"`（另有 `--force`
     pin 与 `upgrade` 两种形态），信任根换成 winget 源。对本分叉是双重冲突：包 id 是上游品牌
     （`chaos update` 不可能装 `xAI.GrokBuild`），且这条路**绕开**本分叉的 `require-sig` /
     ed25519 `.sig` fail-closed 链。**默认建议 skip**，除非明确决定支持 winget 并另设验签。
   - `windows_payload.rs` 的完整性依据是 `.zip.sha256` sidecar（`parse_sha256_sidecar` +
     `sha256_hex_of_file`），摘要由发送字节的一方自己算——正是本轮 remote provenance
     （`crates/codegen/chaos-engine/src/remote/{provenance,artifact_format}.rs`、新 crate
     `xai-grok-signature`）要消除的形态。若移植，必须改接 `xai-grok-signature`。
   - 冲突面：`auto_update.rs` / `lib.rs` / `Cargo.toml` 与本分叉已交付的验签改造同区。
2. **compaction**：上游改了 `xai-chat-state/src/compaction_{utils,image_context}*.rs` 与
   `xai-compaction-transcript/src/lib.rs`；本轮 DCP 复活落在 `common/xai-grok-compaction`
   的 `strategies` 与 `xai-grok-shell` 的 turn loop。同区，按 B4 第 3 条手工合流，禁止整文件
   theirs/ours。
3. **pager 交互层**：`xai-grok-pager/src/app/acp_handler/{background,follow_ups,interactions}.rs`
   有改动，另有 315 个 `xai-grok-pager-pty-harness` 测试文件；与本轮 `/fallback`、`/adhd`
